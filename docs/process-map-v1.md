# Карта процесса разработки с LLM — v1

| Поле                     | Значение                  |
|--------------------------|---------------------------|
| Проект                   | Валидатор пароля          |
| Базовые требования       | `docs/requirements-v1.md` |
| Модель-исполнитель       | DeepSeek Chat             |
| Ответственный за решения | Разработчик               |

## 1. Общие правила

Процесс состоит из шести шагов (**A–F**).

Каждый шаг имеет определённые входные данные, выходной артефакт и условия проверки.

Результат LLM не принимается автоматически. Переход к следующему шагу разрешает разработчик после проверки соответствия
требованиям.

При отсутствии данных, противоречиях или неподтверждённом результате процесс останавливается до разрешения проблемы.

Изменения утверждённых требований оформляются новой версией. Модель не вправе самостоятельно расширять область задачи.

## 2. Шаги процесса

### A — Анализ требований

**Цель:** проверить полноту, однозначность и проверяемость утверждённых требований без изменения их смысла.

**Вход:**

- Полный текст `docs/requirements-v1.md`
- Технические ограничения
- Критерии завершения

**Действие LLM:** выявить неоднозначности, противоречия и риски.

**Выход:**

- Перечень замечаний с привязкой к R01–R11
- Рекомендации по минимальным уточнениям
- Перечень требований без замечаний

**Проверка:** разработчик рассматривает каждое замечание. Изменения требований допускаются только по отдельному решению
с новой версией.

### B — Проектирование проверок

**Цель:** подготовить сценарии проверки программы до появления реализации.

**Вход:**

- Актуальная утверждённая версия требований
- Результат шага A
- Технические ограничения

**Действие LLM:** сформировать тестовые сценарии с входными данными и ожидаемыми результатами.

**Выход:**

- `tests/scenarios-v1.md`
- Идентификаторы T01, T02 и далее
- Связь сценариев с требованиями

**Проверка:** не менее 8 различных сценариев, не менее 3 граничных случаев. Для каждого указаны вход, ожидаемый вывод и
проверяемые требования.

### C — Реализация

**Цель:** создать минимальную Java-программу, реализующую утверждённые требования.

**Вход:**

- Актуальные требования
- Утверждённые сценарии
- Технические ограничения

**Действие LLM:** сгенерировать исходный код Java 17.

**Выход:**

- `src/PasswordValidator.java`
- Пояснение принятых технических решений

**Проверка:** компиляция `javac`, отсутствие внешних зависимостей, соответствие ограничениям и объёму 50–150 строк.

### D — Проверка реализации

**Цель:** сопоставить поведение программы с заранее определёнными ожиданиями.

**Вход:**

- Версия исходного кода
- Утверждённые сценарии
- Результаты локального выполнения

**Действие LLM:** проанализировать предоставленные результаты, выявить расхождения с требованиями.

**Выход:**

- Перечень пройденных и проваленных проверок
- Описание обнаруженных расхождений
- Рекомендация о необходимости исправления

**Проверка:** разработчик сверяет вывод LLM с фактическими результатами локальных проверок. Непроверенные сценарии не
считаются успешными.

### E — Исправление дефекта (условный шаг)

**Цель:** локально устранить подтверждённый дефект.

**Условие запуска:** на шаге D выявлено расхождение либо создан отдельный учебный дефект.

**Вход:**

- Версия программы с дефектом
- Идентификатор нарушенного требования
- Входные данные и ожидаемый результат
- Фактический результат
- Ограничения исправления

**Действие LLM:** предложить минимальное исправление без добавления новых функций.

**Выход:**

- Исправленная версия кода
- Описание изменения
- Перечень затронутых проверок

**Проверка:** повторить проваленный сценарий, связанные проверки и регрессию.

**Ограничение:** не более двух запросов к LLM на исправление одного дефекта. После двух неудачных попыток — остановка и
решение разработчика.

### F — Итоговая приёмка

**Цель:** подтвердить выполнение требований на конкретной финальной версии программы.

**Вход:**

- Финальный исходный код
- Все утверждённые сценарии
- Результаты полной регрессии
- Журнал и подтверждающие материалы

**Действие LLM:** подготовить проект матрицы прослеживаемости и перечень возможных ограничений.

**Выход:**

- Матрица R → T → результат → evidence
- Проект решения о приёмке
- Перечень непроверенных требований

**Проверка:** разработчик самостоятельно подтверждает результаты и принимает итоговое решение.

## 3. Контрольные точки

### KT1 — Допуск к проектированию проверок

**Проверяется:**

- Полнота и согласованность требований
- Результат анализа шага A

**Способ:** ручная сверка с `docs/requirements-v1.md`.

**Успех:** разработчик допускает переход к шагу B.

**Неуспех:** возврат к уточнению требований, создание новой версии и повтор шага A.

### KT2 — Допуск к реализации

**Проверяется:**

- Наличие сценариев с ожидаемыми результатами
- Покрытие требований
- Не менее 8 сценариев и 3 граничных случаев

**Способ:** ручная проверка `tests/scenarios-v1.md`.

**Успех:** разработчик допускает шаг C.

**Неуспех:** возврат к шагу B.

### KT3 — Допуск к приёмке

**Проверяется:**

- Компиляция Java 17
- Результаты локальных сценариев
- Соответствие кода техническим ограничениям
- Наличие подтверждений обнаруженных дефектов

**Способ:** компиляция, выполнение сценариев, сравнение ожидаемого и фактического вывода.

**Успех:** разработчик допускает шаг F.

**Неуспех:** переход к шагу E либо остановка с документированным ограничением. После исправления — повтор шага D.

### KT4 — Финальная приёмка

**Проверяется:**

- Полная регрессия финальной версии
- Матрица прослеживаемости
- Подтверждения выполнения требований
- Полнота журнала и архива

**Способ:** сверка документов и локальных результатов.

**Успех:** решение «Принято».

**Неуспех:** решение «Принято с ограничениями» либо «Отклонено» с указанием причин.

## 4. Независимый аудит карты

До выполнения рабочего шага A карта процесса передаётся на аудит в отдельный чат LLM.

**Аудитор получает:**

- Полные требования и ограничения
- Карту процесса
- Правила контрольных точек

**Аудитор проверяет:**

- Передачу данных между шагами
- Полноту входов и выходов
- Условия переходов
- Возвраты при ошибках
- Роль человека в принятии решений

Аудитор не пишет код и не добавляет функции.

Каждое замечание фиксируется в журнале с решением разработчика: принято, отклонено или требует уточнения.

При необходимости выпускается новая версия карты процесса.

## 5. Пакет передачи

Перед переходом в новый рабочий чат подготавливается пакет передачи:

- Цель и текущий шаг
- Полная актуальная версия требований
- Версии кода и сценариев
- Принятые решения
- Результаты проверок и evidence
- Открытые вопросы
- Полный контракт следующего шага

Отсутствующие данные отмечаются явно.
